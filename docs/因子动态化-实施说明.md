## 2. 架构师实测数据（可直接采信，勿重复测）

| 实测项 | 耗时 | 结论 |
|---|---|---|
| `SELECT MIN(date), MAX(date) FROM factor_panel`（合并成一条） | **31.2s** | 现行 `fingerprint()` 正是这个写法 |
| 同上 + `COUNT(*)` 23.7s + `COUNT(DISTINCT factor)` | **≈66s/次** | 且 `panel_cache.load()` **每读一个因子都调一次** → 24 因子光指纹 ~26 分钟。`DISTINCT factor` 单项实测 **7.4s（热页缓存）/ 31s（冷页缓存）** |
| 拆成 `SELECT MIN(date)` / `SELECT MAX(date)` 各自执行 | **0.00s / 0.00s** | 走索引，零成本 |
| `SELECT DISTINCT date FROM factor_panel` | 9.6s | 全表轴校验可每天做 |
| `SELECT DISTINCT symbol FROM factor_panel` | 13.8s | 同上，合计 24s 可接受 |
| 范围查询 `DISTINCT date WHERE date > ?` / `DISTINCT symbol WHERE date > ?` | 2.2s / 0.2s | 尾部增量检测日频零负担 |
| `panel_cache/` 现状 | 7 因子 229MB | 另有一个**孤儿文件 `atr_pct14.npy`**（不在 meta 里，上次中断残留），需清理 |
| 磁盘 D: | 剩 62G | staging 双份缓存（+685MB）安全 |

**根因判断**：`fingerprint()` 含 `max(date)` 只是表象，真正的放大器是「一次性全表聚合」+「每次 load 都调」。两者必须一起改。

### 2.1 逐日 IC 序列复用验证（R1，已实测）

`data/factor_eval.json` 每个因子都带 `ic_series`（格式 `[[date, ic], ...]`），实测：

| 验证项 | 结果 |
|---|---|
| 覆盖 | **24/24** 因子均有 `ic_series`，无缺失 |
| 末端日期 | 全部 `2026-11-06`；面板最新 `2026-11-13` → **差正好 5 个交易日**（= `meta.horizon`） |
| 口径 | `meta.horizon=5`、`meta.entry=s1_open`、**`meta.min_stocks=30`**（见 §3 决策 9） |
| 可复现性 | 用缓存面板 + `load_forward_returns(5, s1_open)` 独立重算 `mom60`：n=1335 与存档**同长**，重叠区**最大绝对差 2.04e-06**（全部是 float32 排名并列舍入）→ 逐日 IC 稳定可复现 |
| 独立重算末端 | 同样止于 `2026-11-06` → **约束 A 由数据本身印证**：T 日 IC 的最晚可用日 = 面板最新 − horizon |
| 单因子缓存读取 | `panel_cache.load('mom60')` 单次 **38.5s**（被 `fingerprint()` 拖累）→ 24 因子 15 分钟，T01 的必要性再获数据支撑 |
| 价格宽表 | `close`+`open` 合计 **54.7s** → 整个 pipeline **只加载一次**，ts 追加与滚动验证共用同一份 `fwd` |

**结论**：逐日 IC 一旦算出即稳定（横截面相关，不随后续新增数据变化），因此滚动验证**不需要每天重算 1420 天 × 24 因子**，读持久化序列做窗口切片即可。**但只存 IC 不够**，必须同时存逐日 10 组收益——原因见 §5.4。

## 3. 主理人拍板的 10 项决策（已定，不再讨论）

1. **`fingerprint` 性能改造前置为 T01 第一件事**。这不是新增范围，是「≤5 分钟」达标的必要条件。
2. **缺口补齐设 `MAX_DAYS=30` 上限**：连续 30 个交易日未跑时，本次只补最近 30 日，剩余下次继续；仍超限则提示改走全量重建。
3. **冷启动走「上线前一次性手动」**：补齐 17 个缺失因子缓存需 60–90 分钟，不能塞进 16:10 定时任务。日常任务启动时先 `coverage()` 断言 24 因子齐备，不齐则 `exit 2` 并给出明确提示。
4. **sync 失败被拦后，sync 重试成功允许当日补跑 factor**。用 `last_factor_attempt_date` 做尝试级去重、`last_factor_ok` 做成功级去重。
5. **`recentOnly` 冻结可接受**：每日重算不再生成该变体，只把上一版原样继承并打 `deprecated:true`。它作为历史断面冻结是合理的，不要求它继续随新股更新。
6. **必须加 `evalAsOf` 字段**：每日 pipeline 不重跑 `factor_eval.py`（小时级），所以 `factor_api.json` 里的 `ic/tNw/mono` 仍来自上一次全量评估。页面会同时出现「数据截止 2026-11-16」与「IC 基于 11-13 评估」——必须把 `evalAsOf`（取 `factor_eval.json` 的 mtime）显示在徽标展开的技术细节里，并注明「单因子 IC 统计每次全量评估才更新，非每日更新」。
7. **`recentOnlyMergedAt` 废弃**（页面/报告均未读，已 grep 确认）。`generatedAt` 保留字段与类型但语义降级为「本文件写出时刻」，前端不得用于「上次计算」文案。
8. **`obv_slope20` 截断等价性有前提**：它用 `cumsum`，绝对水平随截断起点变化，但因子取 20 日 OLS 斜率，对常数偏移不变，故仍等价。必须在 `factors/compute.py` 顶部加注释：**新增因子必须窗口有界或对偏移不变，否则必须全量重算**。`obv_slope20` 列入 T02 强制覆盖用例。
9. **`min_stocks` 统一取 100，不复用存档的 30 口径**：`factor_ts` 本来就必须全量扫一遍补 `groups`，复用存档 `ic` 只省 **52 秒**（只补 groups ≈48s vs ic+groups 全算 ≈100s），却换来「`recent_validity` 用 100、`rolling` 用 30」两套口径并存 + 页面加注说明。**统一 100、一次性全量重算（100 秒）**。但存档的 30 口径 `ic_series` 不浪费，升级为**独立对账源**（规则见 §5.7）：差异只记 warning，**不作重建触发**。
10. **销毁性操作一律留退路**：任何「截断 / 覆盖 / 删除」必须先留 `.bak` 副本；重算结果需与 `.bak` 重叠区一致才允许替换；不一致则保留 `.bak` 并把该因子置 `state="suspect"`，滚动验证跳过它、页面标注。**禁止「判定 → 直接截断」这类不可逆写法**（原 R1 方案的 `ts.last > panelMax-horizon → 直接截断重算` 已按此废弃，见 §5.6 第 6 条）。

## 4. 每日 pipeline 的动作序列（单一进程，退出码即结论）

`plan → 增量算面板 → 写库 → 缓存 staging+verify+提交 → ts 追加 → 滚动验证 → 打分/导出 → finish`

**明确不重跑 `factor_eval.py`**（小时级全量评估）。这是审计边界，不是遗漏。

预算推算（R1 修订后）：plan 15s（**冷页缓存时 +30s，见下**）+ 计算 120s + 写库 8s + staging 40s + verify 35s + **价格宽表 55s（全流程只加载一次，惰性）** + ts 追加 20s + rolling 15s（纯切片，面板已加载）+ score 150s + export 60s ≈ **8.5 分钟**（冷启动 9 分钟；原估 11 分钟）。
（P0-2 的「≤10 分钟」只指前四步 ≈ 3.5 分钟；整体远低于 60 分钟子进程超时）

**冷启动的 30 秒从哪来**：`structure_sig()` 要执行一次 `SELECT DISTINCT factor`，进程刚起时索引页还没进 page cache，实测 **31s**（热态 7.4s）。它在进程内 memo，一次运行只付一次；且 `stage_append` 直接复用 `meta.sig` 不再重算，所以**日常路径可以绕开**。计划预算里不要假设 plan 恒为 15s。

## 5. 缓存与时间序列持久化设计（P0-2 / P0-4 达标前提）

### 5.1 指纹拆两层，日常不失效

```
结构签名 sig = "min=2021-01-04|nf=24|fh=<24 个因子名排序后的 sha1 前 8 位>"
  ← 由 SELECT MIN(date)（0.0s）+ SELECT DISTINCT factor（7.4s 热 / 31s 冷，进程内 memo 一次）
  ← 刻意不含 rows / max(date) / symbol 数
轴（append-only）= meta.dates[] / meta.symbols[]，只追加、永不重排、永不重算
尾部增量 = SELECT DISTINCT date|symbol FROM factor_panel WHERE date > meta.maxDate（2.2s/0.2s）
```

规则：
- `sig` 变（min date 变 / 因子集合变）→ 结构失效，触发**全量重建**（39 min，走 `rebuild_panel.py`）
- `sig` 不变、只有尾部新日期 → **追加**
- 尾部新 symbol（IPO）→ 追加**列**
- 全量轴校验发现「中间日期出现新 symbol / 有日期缺失」→ 轴不兼容 → **全量重建**（增量无法自愈的唯一情形，必须显式判定，不能悄悄错位）

### 5.2 npy 追加用 staging 双写 + 原子发布

`np.load(mmap_mode="r")` 只读；`open_memmap` 改不了 shape 头，就地改写中断会写坏唯一一份缓存。所以：

```
data/panel_cache/_stage/<factor>.npy   ← 新形状 (R+ΔR) × (C+ΔC)
  = 旧文件 memcpy 到 [0:R, 0:C]（已有行号/列号完全不变）
  + 新行由 DB 回读 targetDates 切片 reindex 到新轴填在 [R:, :]
data/panel_cache/_stage/meta.new.json  ← 新轴 = dates + new_dates, symbols + new_symbols
```

提交序列（只有 verify 通过才进）：
```
verify_stage().ok == True
  → 24 × os.replace(_stage/x.npy → x.npy)
  → os.replace(meta.new.json → meta.json)   # meta 是唯一"提交指针"，必须最后
```

崩在提交前：正式缓存完整、`meta.json` 未变，旧轴继续可用。`load()` 用 `meta` 的轴长度做形状校验，长度不符的孤儿 npy 一律视为「缓存不完整」返回 None，**不会出现「新矩阵被旧轴解释」的错位**。

代价：24 × 28.5MB 读 + 28.6MB 写 ≈ 1.4GB I/O，SSD ~40s。替换掉的是「全量重导 24×3.5min = 84 分钟」。

### 5.3 为什么增量与全量逐位相等

`compute_series` 只用滚动/因果窗口，最大窗口 250 日（`dist_high250`），最大 `min_bars` 141（`mom120`）。取 `WARMUP_BARS=300`（>250+20 skip）后逐股读 `date >= calc_start` 的 320 行，与读全历史算完再切片**数学等价**。

`compute_series` 的 `n_rows < min_bars` 分支在截断后仍成立（300 > 141），不会误置 NaN。唯一非窗口有界的是 `obv_slope20`（`cumsum`），但其因子取 20 日 OLS **斜率**、对常数偏移不变，故仍等价——已列入 T02 强制覆盖用例。

### 5.4 逐日 IC 与逐日 10 组收益**必须一起**持久化（R1 核心）

**为什么只存 IC 不可用**：滚动验证的选因子判据复用 `export_factor_api.verdict_of(f)`，判定链是：

```
t_nw = f.rank_ic.t_nw        ← 逐日 IC 序列可提供 ✔
mono = f.monotonicity        ← 需要「窗口内 10 组平均收益 → 组间 spearman」✘ IC 序列给不出

if t_nw is None:                          → "数据不足"
if abs(t_nw) < 2:                         → "未达门槛"
if mono is not None and mono >= 0.5:      → "值得复核"      ← 选中
if mono is not None and mono <= -0.5:     → "方向需翻转"    ← 选中
return                                    → "仅统计显著"    ← 不选
```

**若 `mono` 为 None，所有统计显著的因子都会落到「仅统计显著」→ 选中集合恒为空，滚动验证一个因子都选不出来，而且全链路不报任何错。**
这是本方案最容易再犯的错（主理人第一版方案即漏此点），务必守住。

因此持久化的是**一对原生量**，由同一次横截面计算产出（增量成本≈0）：

| 量 | 含义 | 口径 |
|---|---|---|
| `ic[d]` | d 日横截面 Spearman IC | **未乘 direction 的原始值**（见 §10 第 12 条）；`min_stocks=100` |
| `groups[d][1..10]` | d 日 10 组等权平均未来收益 | `group_returns` 内部已按 direction 归正，组 1 = 预期最好 |

窗口单调性随时用 `monotonicity_of(groups_win.mean(axis=0))` 重算。该函数从 `factor_eval.evaluate_factor` 抽出，**全库唯一一份**，禁止在 `rolling_eval.py` 里另写一遍。

**为什么这两个量缺一不可（本轮生产缺陷的根因层解释）**

| 量 | 是否乘先验方向 | 用来回答什么问题 |
|---|---|---|
| `ic[d]` | **否**（原始值） | 「这个因子有没有预测力」→ 算 `t_nw`；也是方向判据的数值基础 |
| `groups[d]` | **是**（组 1 = 先验认为最好的组） | 「它的方向是不是和我们的假设反了」→ 算 `mono`，`mono <= -0.5` 的语义恰恰就是**先验方向反了** |

两个量合起来才能同时回答上面两个问题；缺任一个，方向判定就只能拍脑袋。

**关键在于**：数据层其实是对的——`groups` 确实按先验归正了，`mono` 确实能反映反号。本轮缺陷错在**消费层没读这个结论**（见 §5.9），不是数据层算错。所以修法不在 `factor_ts`，而在打分链路。

### 5.5 落盘结构：`data/factor_ts/`（每因子独立轴）

```
data/factor_ts/<factor>.npz    dates(str[U10]) | ic(float32[n]) | groups(float32[n,10])
data/factor_ts/meta.json       {horizon, entry, minStocks, nGroups,
                                factors:{name:{n, first, last, state, suspectSince}},  # state: ok | suspect
                                sig:{panelMinDate, panelRebuildId, factorSig},
                                builtAt, lastAppendRunId, source,
                                reconcile:{checkedAt, commonFactorDays, maxAbsDiff, extraDays, extraPct,
                                           state, firstWarnAt, dataWarn, caliberWarn,
                                           suspectFactors:[...]}}
```

`reconcile` 段的字段语义与派生规则见 §5.7，**`state` 必须由 `factors[].state` 派生，禁止另写一套判定**。

**为什么每因子一个独立文件、刻意不做共轴**：各因子预热期不同（`turn20` 起 2021-01-29、`dist_high250` 起 2021-04-02、`mom60` 起 2021-05-07）。共轴必然引入 NaN 或被短序列稀释。独立轴后，「最近 120 日」在**各自轴上**切片：

- 可用天数 < 20 → 该因子本期判 `unknown`、不入选（与 `recent_validity` 阈值一致）
- **禁止**把不同长度的序列强行对齐成同一窗口

体积：24 × (1400 + 1400×10) × 4B ≈ **1.5MB**，可忽略。

**初始化（一次性，~100 秒）**：按 `min_stocks=100` 全量重算 `ic` + `groups`（不复用存档的 30 口径）。

**顺序是硬约束，必须用代码断言守住**：`factor_ts.ensure()` 入口先做 `panel_cache.coverage()`，24 个不齐直接 `exit 2`（提示 `--build-all`）。原因不是「慢一点」，而是**会静默降级成完全不同的东西**：

| 前置状态 | 初始化耗时 | 是否报错 |
|---|---|---|
| T01 已修 + 24 因子齐备 | 24 × 0.03s ≈ **1 秒**（加 IC/分组计算约 100s） | — |
| T01 已修 + 缓存缺失 | 24 × 逐因子 SQL 回落 → **分钟级** | **不报错**（`load_panel_wide` 静默回落，见 §10 第 15 条） |
| T01 未修 | 24 × 38.5s ≈ **15 分钟** | 不报错 |

第三种情况只会让人觉得「今天特别慢」，第二种连慢的原因都看不出来。所以入口断言不可省。

**每日追加（~20s）**：

```
last = meta.factors[name].last
# panelDates 必须是「本步写入后从 factor_panel 读出的实际日期并集」，
# 不是 plan.targetDates：残日会被 MIN_SYMBOLS_PER_DAY 剔除，两者可能不等。
# 若按 plan.targetDates 追加，被剔除那天会因为没有面板行而算出 NaN 或空 IC。
panelMaxDate = SELECT MAX(date) FROM factor_panel
targets = [d for d in panelDates if last < d <= panelMaxDate - horizon]   # 天然排除最后 5 天
per d:  ic[d]     = daily_ic(panel.loc[[d]], fwd.loc[[d]], min_stocks=100)
        groups[d] = group_returns(panel.loc[[d]], fwd.loc[[d]], direction)[1..10]
```

最后 `horizon` 天算不出 IC 是**必然**（缺未来收益）：**不追加行、不补 0、不报错**，序列自然终止于 `panelMax - horizon`。

**滞后天数怎么判**：正常是 `== horizon`；但 `min_stocks=100` 会把「当日有值股票数落在 30~100 之间」的日子判为无 IC，所以滞后**可能 > horizon**。
**`滞后 >= horizon` 都正常，只有 `< horizon` 才是错误实现** —— QA 不要写 `== horizon` 的断言。

### 5.6 失效与重建矩阵（6 条）

| # | 条件 | 动作 |
|---|---|---|
| 1 | `meta.horizon / entry / minStocks / nGroups` ≠ 当前配置 | **全量重建**（防改口径后静默复用错数据） |
| 2 | `meta.sig.panelRebuildId` ≠ `data/panel_rebuild.json` 的 `rebuildId` | 全量重建（面板被全量重建 → 老日期因子值/分组可能已变） |
| 3 | `meta.sig.factorSig`（因子集合哈希）不一致 | 全量重建 |
| 4 | `meta.sig.panelMinDate` 不一致 | 全量重建 |
| 5 | 某因子文件缺失 / `dates` 非严格递增 / `n(ic) ≠ n(dates)` | **只重建该因子** |
| 6 | `ts.last > panelMaxDate - horizon` | **保护式重算**（见下），**绝不直接截断** |

第 6 条的正确写法（原「截断到 `panelMax - horizon` 后重算」**已废弃**——截断不可逆，判定若有 bug 就销毁了正确数据）：

```
1. cp <factor>.npz → <factor>.npz.bak            # 先留退路
2. 按「不超过 panelMax - horizon」重算该因子全序列到临时文件
3. 与 .bak 在重叠区间逐日比对（容差 1e-5）
   · 一致   → os.replace(临时 → 正式)，删除 .bak
   · 不一致 → 正式文件保持不动、保留 .bak，
              meta.factors[name].state = "suspect"
              滚动验证跳过该因子，页面标注「数据可疑，已跳过」
```

`panel_rebuild.json` 由 `rebuild_panel.py` 在替换成功后写出：`{rebuildId, at, rows, dates, symbols}`（约 6 行代码）。原来靠 `fingerprint()` 里 `max(date)` 勉强充当的「面板是否换过」职责，由此改为**显式重建 ID**。

### 5.7 与 `factor_eval.json` 对账（只作可见性，不作重建触发）

重算本身已经是全量重建，所以「不一致」不再是重建理由；但存档是**独立口径（min_stocks=30）**的天然参照，值得每天比一次：

```
common = 存档日期 ∩ 重算日期
在 common 上逐日比 IC，容差 1e-5          # 实测最大差 2.04e-06，留 5 倍余量
extra  = |存档有、重算无| 的天数            # 30 vs 100 的口径差异天
extraPct = extra / len(存档)
extraPct > 5%  → caliberWarn = true（字段定义见下方落地要求）

不一致 → 记 warning + 以重算为准，不重建
         原因：更可能是前复权漂移（已知缺陷）而非代码错误，重建解决不了，但记录能让它可见
```

**决策（主理人）：保持 warn-only，但 warning 必须可见，不能只落日志。**

理由：复权漂移是**每天都会存在**的偏差（腾讯按最新价重算全历史）。如果 warning 只写进 `factor_ts.log`，用户每天早上看到的 IC 就是悄悄偏掉的数字，却没有任何提示——这违反 §10 第 8 条「失败不可静默」的同一个精神。

落地要求：

```
factor_ts/meta.json 的 reconcile 段：
  {checkedAt, commonFactorDays, maxAbsDiff, extraDays, extraPct,
   state, firstWarnAt, dataWarn, caliberWarn, suspectFactors:[...]}
  ⚠ `commonFactorDays` 是 **(因子, 日) 的累加**，不是交易日数（24 × ~1400 ≈ 33187）。
     旧名 `commonDays` 会让读者以为重叠了 33187 个交易日。
```

**两级 state 的分工：派生，不独立判定**

```
单因子（唯一的事实来源）
  meta.factors[name].state        : ok | suspect
  meta.factors[name].suspectSince : "YYYY-MM-DD"（首次被标 suspect 的日期）
  suspect = 该因子保护式重算未通过 / 文件损坏 → 滚动验证跳过该因子

全局（必须由单因子派生，禁止另写一套判定，否则两处必然分叉）
  meta.reconcile.state =
    "suspect"   任一 factors[].state == suspect        ← 优先级最高
    "warn"      maxAbsDiff > 1e-3  或  extraPct > 5%
    "ok"        其余
  另存两个布尔供文案区分：
    dataWarn    = maxAbsDiff > 1e-3
    caliberWarn = extraPct > 5%
```

**为什么 `dataWarn` 是 1e-3 而不是 1e-5**：这里比的是**跨口径**（存档 `min_stocks=30`
vs 本模块 100）的逐日 IC，两种口径下「当日有效标的集合」本就不同，IC 必然有差。
生产实测（24 因子 × 33187 个 (因子,日)）：P99=2.33e-05、P99.9=5.92e-05、max=2.04e-04，
超过 1e-4 的只有 5 点。用 1e-5 卡它，结果是 `dataWarn` 天天为真、`state` 永远 `warn`
—— 天天亮的告警等于没有告警。取 1e-3 = 实测最大值的 5 倍，同时比真实数值错误
（用例注入 +0.05）小两个量级。同口径的 `.bak` 重叠比对仍用 `PROTECT_RTOL=1e-5`，
两者不可混用。

**两类偏差不能合并成一句**（性质不同，处置不同）：

| 字段 | 含义 | 性质 |
|---|---|---|
| `maxAbsDiff > 1e-5` | 重叠日期上逐日 IC 的数值差 | **数据问题**：可能是复权漂移，也可能是代码差异 |
| `extraPct > 5%` | 「存档有、重算无」的天数占比 | **参数问题**：100 口径太严，把太多天判成无 IC |

**透出路径与页面文案**

```
freshness.cacheVerify.reconcile = {state, extraDays, extraPct, maxAbsDiff, firstWarnAt,
                                   suspectFactors}        （/api/picks 与 /api/factors 都有）
rolling.skippedFactors          = [{factor, reason, since}]

页面徽标展开的技术细节里显示（按档位）：
  state=ok
      → 不显示
  state=warn（dataWarn 单独成立）
      → 「对账偏差：重叠日最大差 3.2e-04（自 2026-11-16 起）」
  state=warn（caliberWarn 单独成立）
      → 「口径差异：38 天（6.1%）因样本不足 100 只被排除」
  state=warn（两者同时成立）
      → 上面两行**都显示，不合并成一句**
  state=suspect
      → 红色「N 个因子 IC 未经复核，滚动验证已跳过：mom60、turn20」
         · N 必须写出来（只列名字不带数，用户不知道是 1 个还是 13 个）
         · 因子 > 5 个时只列前 5 个 + 「等 N 个」
```

**`skippedFactors.since` 的语义（必须写清，否则用户无法理解历史各期）**

```
skippedFactors: [{"factor":"mom60","reason":"suspect","since":"2026-11-16"}]

· suspect 是「当前状态」，而 rolling.periods 覆盖历史各期
· 早于 since 的期：该因子正常参与（当时数据可信）
· since 及之后的期：该因子被跳过
· 因此逐期因子数会随时间变化 —— 有 since 才能回答
  「以前那些期算的时候跳过了吗」，这种变化才永远可解释

另有两个「因子数」不能混（T03 验收时实测出来的）：
  n_considered  进 rows 的个数（含被判「数据不足」的）
  n_evaluable   真正能评估的（verdict ≠ 数据不足 且有 t 值）
  n_factors     保留字段名，值 = n_evaluable（旧实现取 len(rows)，把预热期不够、
                窗口内一天数据都没有的因子也算成有效因子）
  早期期 `n_evaluable < n_considered` 是正常的：预热 141 根 K 线的因子在那时尚无 IC。
```

**`firstWarnAt`**：复权漂移是天天存在的已知缺陷，`warn` 一旦触发基本不会消失。只存最新一次 warning，用户与 QA 都无法区分「今天新出现的偏差」和「已存在半年的老偏差」，提示会变成墙纸。必须存首次触发时间。

### 5.8 逐期定方向与 walk-forward 打分（T06，用户已拍板）

**要消掉的是两处前视，不是一处**

| # | 前视 | 现状 |
|---|---|---|
| 1 | 候选因子按**全样本** t 值挑 | `factor_score.load_candidates(evald)` 读 `factor_eval.json` 的全样本结论 → 2021 年起每一期都用了「2026 年才可能知道」的因子名单 |
| 2 | **方向**用先验 `registry.direction` | `factor_score.py` 只有 `df = panels[n] * int(get_factor(n)["direction"])`，全库没有任何一处按 verdict 取反 |

第 2 条是本轮发现的具体缺陷：`rolling_eval.SELECTED_VERDICTS = ("值得复核", "方向需翻转")` 把「方向需翻转」选进来，而它的定义就是 `mono <= -0.5`（**与先验相反**）；打分端却照样乘先验方向 → 选进来、又反向使用。实测规模：12 个代表因子里 6 个属此类（`dist_high250 / dist_low250 / mom120 / mom20 / mom60 / obv_slope20`，全部 `direction=+1`）；滚动 70 期中 57 期含翻转因子，入选 533 次里 173 次（32.5%）是翻转因子，其中 164 次（30.8%）以**负贡献**计入。

**判据（唯一一句，不得改写）**

> 某日 `d` 采用「**最近一期 `t` 满足 `ic_cutoff(t) <= d - horizon`**」的结论；`ic_cutoff(t)` 之前没有任何可用期时，**不向前回填**。

两个常见写错方式，都不许出现：
- `cut < d` —— 会放进 cutoff 落在 `(d-horizon, d)` 的那一期，等于用到了 `d-4..d-1` 的收益
- `cut <= d` —— 直接就是约束 A 里那个错误

**实现规定**

| 项 | 规定 | 理由 |
|---|---|---|
| 期网格 | 复用 `period_indices(step=20)` | 与滚动验证同一套期，否则两份结果不可比 |
| 期信号 | 复用 `evaluate_period(...)` | 它内部只用 `<= ic_cutoff`，不另写选因子逻辑 |
| 有效方向 | `d_eff = d_prior × (+1「值得复核」/ -1「方向需翻转」)` | 「翻转」是**结论**不是修饰词，必须落到符号上 |
| 权重 | **等权**，不用 `|t|` 加权 | 方向判断刚刚出过错，按 `|t|` 加权会把错误方向的权重放大 |
| 逐日追溯 | 每天记 `signAsOf`（该日生效的期号与 cutoff），形成**阶梯函数** | 用户问「这天为什么这么算」时必须能答 |
| 缺失处理 | cutoff 之前无可用期 → **不回填**，该日沿用「尚无结论」状态 | 回填等于用未来数据 |
| 输出 | `validation`（walk-forward，**主指标**）与 `validationFullSample`（对照，必须标「含轻度前视」）；**名单只有一份** | 两版名单并列会让用户以为可以选 |

**方向缺陷的量化证据（只读反事实，`D:\tmp\flip_test.py`，用缓存 npy，不写项目文件）**

```
基线（只乘先验）      IC +0.0390  t_NW +6.74   第1组 24.20%   第10组 +5.58%
修正（按判定翻转）    IC +0.0733  t_NW +9.59   第1组 30.43%   第10组 -3.77%
最新交易日 Top10 重合 0/10
```

⚠ 这版**含前视**（用全样本判定回测全样本），**只能当上限**。无前视的证据在滚动序列里：入选组合的有效 IC（`icMean × 先验方向`）期级均值 **+0.0269 → 按判定翻转后 +0.0599**。
第 10 组年化转负（+5.58% → −3.77%）尤其值得记：它说明原来的"多头空头都赚钱"其实来自方向错配，不是因子真实的多空能力。

### 5.9 「判定 → 选中 → 使用」这条链：本轮最值得记住的架构教训

缺陷不是任何单个模块写错了，而是**三个模块各自看都自洽、合起来矛盾**：

| 环节 | 位置 | 它「以为」的事 |
|---|---|---|
| 判定 | `export_factor_api.verdict_of` | 「方向需翻转」= *按先验方向使用会反向暴露*（文案已经这么写了） |
| 选中 | `rolling_eval.SELECTED_VERDICTS` | 这类因子**值得选进来**（确实值得——只要把方向翻过来） |
| 使用 | `factor_score.py` | 只乘 `registry.direction`（先验），**没有任何按 verdict 取反的分支** |

三者拼起来就是：**把「必须先翻方向」的因子选进来，然后按没翻的方向用**。而这个组合矛盾没有任何一处报错——`verdict_of` 的文案是对的、`SELECTED_VERDICTS` 的选择是对的、`factor_score` 的乘法也是对的（对「值得复核」这类因子而言）。

**为什么 345 项测试全绿仍发现不了**：没有一条断言覆盖「判定 → 选中 → 使用」的**端到端语义**。每个模块的单测都在自己的假设里自洽。

**因此立一条硬规则**：

> **凡是新增一个 verdict 档位进入 `SELECTED_VERDICTS`，必须在同一处同时声明消费端如何处置它——用什么符号、什么权重、缺失时怎么办。三者缺一不许加。**

配套的检查手段（T06 验收里落实）：
1. 对 `SELECTED_VERDICTS` 的每个成员，打分链路必须在代码里有对应的符号分支；用一条单测断言「遍历所有档位都能得到预期的 `d_eff`」，档位增减时这条测试会红
2. 一条端到端断言：`d_eff` 的符号必须等于 `verdict → sign` 映射表的结果，**不允许**在别处再从 `registry.direction` 直接取符号

## 6. 约束 A：前视泄漏的唯一入口，必须堵死

**唯一入口**：IC 的计算需要 `fwd`，`fwd[d]` 用到 `open[d+1]` 与 `close[d+h]`。因此**在时点 T 选因子时，可用于评判的 IC 序列最后一行最多到 `dates[idx(T) - horizon]`**。

```python
def ic_cutoff(dates, t_idx, horizon):
    j = t_idx - horizon
    if j < 0: raise ValueError(...)
    return dates[j]          # 例：T=2025-03-14(idx 1000)、h=5 → cut=2025-03-07

# 使用处（唯一写法）
ic_win = ic.loc[:cut].iloc[-select_window:]
# 运行时断言（第一道：切片层）
assert ic_win.index.max() <= cut
# 运行时断言（第二道：数据层）—— ts 的末端天然滞后 horizon
assert ts_last_date <= panelMaxDate - horizon     # 滞后 >= horizon 正常，< horizon 必为错误实现
```

第二道断言几乎零成本，却能抓住「用 NaN / 前向填充凑出 T 日 IC」这一类实现错误，比任何测试都便宜。

**关键认知**：per-date 预计算整条 IC / 分组收益序列、再按 `<= cut` 切片，**本身不泄漏**——序列第 d 个元素只是 d+h 及以前数据的函数。泄漏只发生在「切到 `<= T`」。所以「一次性预计算 + 按期切片」这个优化与正确性不冲突，也是能压到 5 分钟内的关键。

**三套测试（必须全绿）**：
1. `test_cutoff_equals_T_minus_h`：断言 `period.icCutoff == dates[idx(T)-h]`。抓 `<= T` 版本必挂。
2. `test_future_corruption_invariance`（**主力**）：把 `close/open` 在 `date > T` 的数据按**逐股乘数** `exp(N(0, 0.35))`（每只股票各自的乘数不同，固定随机种子）扰动后重跑该期，断言 `factors` 集合与 `ic` 数值**逐位相等**。错实现读到 `(T-h, T]` 的 fwd 会变 → 必挂。
   - **必须同时保留一条反面证据断言**：改用**统一乘数**（如整体 ×1.37）扰动时，正确实现与「切到 `<= T`」的误实现结果**完全相同**（实测两者 `tNw = -4.3270548` 一字不差）。这条不是冗余，是防止将来有人为了「简化」把扰动改回统一乘数——那样用例会变成永远通过的空壳。
   - 实测对照：逐股乘数下 正确 `tNw = -4.3270548` / 误用 `cut=T` `tNw = -4.3869715`，**有差异才说明用例有牙齿**。
3. `test_truncation_invariance`：数据截断到 `<= T` 重跑，断言集合相等，并额外断言 `ic` 也相等。

> 注意：PRD 原本只要求「截断重跑」，但它对少量行不敏感、因子集合可能照旧，抓不住 `<= T` 版本。所以以第 2 套为主力。

**为什么必须是逐股扰动（原理）**：Spearman IC 只看**横截面排名**。整体统一乘数是单调变换，不改变任何一天的排名、IC 一分不差——所以它验证不了任何东西，却能在验收单上打勾写「无前视已验证」，比不测更危险。**只有能改变横截面相对位次的扰动，才具备检出力。**

**滚动验证无有效期时的降级语义（不中止）**

「滚动算不出来」和「整个计算失败」是两种严重程度，不能混成同一个红灯：

- **不中止**：继续打分与导出，`factor_run.ok = true`，另置 `partial = true` + `warnings[]`（写明原因，例如「可用期数 < 2」）；`freshness.state` 仍为 `fresh`（数据确实是最新的）；滚动卡片显示「本次无有效期：<原因>」
- **只有「连打分都做不出来」**（如全部因子被跳过、面板为空）才 `exit 4` 硬失败

理由：把「部分可用」按失败处理，页面会亮红灯，用户与 QA 会去查一个不存在的故障，而真正的问题（滚动期数不足）反而被盖住。

### 5.10 扣费后验证与反自欺门槛（T07/T08）

**三个决定性认知**（写在前头，避免有人用错误证据验收）：

1. **统一费率从 IC 里看不出来**。`net = (1+gross) × k(卖出日) − 1`，`k` 只依赖日期时是横截面单调变换 → Spearman IC 与 NW t **一分不差**（`grossIcMean == netIcMean` 已在 `test_trade_cost.py` 里硬断言）。所以扣费验证**必须看净分组收益 / Top10 纸面组合**，IC 继续保持毛口径并在 `validation.icCostNote` 明写"统一费率不改变排名，IC 天然不含成本信息，不要拿 IC 证明扣费后有效"。这与 §6 的"统一乘数抓不住前视"是同一类陷阱。
2. **费率必须按卖出日 `dates[i+h]` 选档**，不能用今天费率倒灌全 history——印花税 2023-08-28 从 1‰ 减半到 0.5‰（卖出单边）、过户费 2022-04-29 从 0.02‰ 降到 0.01‰（双向），用今日值回溯就是新前视。实现上 `rate_table()` 返回**3 段带 from/to 的费率时间表**（不是单一 dict），`rate_at(sell_date)` 是唯一定档入口。当前一轮 31.2bp（佣金万三双边 + 印花 5bp 卖出 + 过户 0.1bp 双向 + 滑点 10bp/边），翻倍 62.4bp。滑点是**无官方来源的保守假设**，`cost` 段标 `assumption:true`，交付时必须向用户显式说明。
3. **50 笔门槛拦「能不能说有效」，不拦「能不能出名单」**。`n_trades>=50 && n_buy_dates>=10 && n_days>=50` 三条件全满足才 `gate.passed=true`；不足时 `evidenceGate.level=insufficient`、名单照写、琥珀横幅「样本不足 N 笔（门槛 50），本轮不能判定有效——当观察清单看，别照着买」、KPI 显示样本不足、**绝不亮绿**。`enforce_gate=True` 只在配置层显式开启（用于"可实盘候选"出口），此时 `EvidenceGateError` 在 `_write_json_atomic` 之前抛，页面保留旧名单、不出现"新名单 + 更新失败"的自相矛盾。

**产物六段契约**（`factor_score.json`，字段名以后端 payload 构造为准，前端 T09 已读死这些键）：

| 段 | 关键字段 | 消费者 / 不变量 |
|---|---|---|
| `cost` | `rates`(3 段费率表)、`roundTripBps=31.2`、`assumedPositionNotional=20000`、`minCommissionBinding`、`priceAdjust=qfq`、`sources` | 前端文案标"滑点是假设值"；不可伪造费率来源 |
| `settlement` | `ok`、`nUnsettled`、`nUnbuyable`、`nUnbuyableExcluded`、`fwdRecomputeMaxAbsDiff`、`notCovered` | **`volume_wide` 必须传入**：volume 的 0 保留为 0（价格<=0 转 NaN，但成交量 0 是真实"不可买"信号）；`paper_trade` 同步剔除，不许"settlement 报不可买、交易照买"；拿不到宽表时 `notCovered` 明写，不假装查过 |
| `validation.costed` | `n_trades`、`n_buy_dates`、`n_days`、`netTop10Annual`、`netTopSpreadAnnual`、`tNw`、`gate{requiredTrades,actual,passed}`、`verdict` | verdict 值域**小写** `pass\|weak\|fail\|insufficient`；`netTop10Annual` 是判定主指标 |

## 7. 约束 B：`factor_run.json` 是唯一时间源

```json
{
  "runId": "20261116T161012",
  "startedAt": "2026-11-16T16:10:12",
  "finishedAt": "2026-11-16T16:22:11",
  "targetDates": ["2026-11-16"],
  "ok": true, "cost": 719.4, "error": null, "trigger": "scheduler",
  "verify": {"ok":true,"checked":120720,"maxRelErr":1.2e-07,"mismatch":0,
             "axis":{"ok":true,"dates":true,"symbols":true,"mode":"tail"}},
  "running": null

```

- 写两次：`begin()` 只填 `running`（不动顶层）；`finish()` 写顶层并清 `running`。两者都 `.tmp → os.replace`
- **`running` 是本文件作为「状态文件」才有的字段**：只供**实时读取**（且按 §8 的 90 分钟有效期守卫使用），**不得复制进任何导出文件**（`factor_api.json` / `factor_score.json` 的 `freshness`），见 §8 与 §10 第 16 条
- **顶层字段永远是「上一次已结算的运行」**
- `lastCalcAt = finishedAt`（未结算则 `startedAt`）、`lastCalcOk = ok`、`lastCalcError = error`
- 业务时间只从这里读；任何模块不得自行 `time.strftime` 生成「上次计算时间」

**`verify` 段的完整形状（页面只读前 5 个，其余是给 QA/排障的探针，缺一不可）**

```json
"verify": {
  "ok": true, "checked": 120720, "maxRelErr": 1.2e-07, "mismatch": 0,
  "axis": {"ok": true, "dates": true, "symbols": true, "mode": "tail"},
  "price":   {"loaded": true, "cost": 54.7, "horizon": 5, "entry": "s1_open",
              "dates": 1421, "symbols": 5030},
  "ts":      {"appended": 2, "factors": 24, "skipped": []},
  "rolling": {"n_periods": 64, "skippedFactors": []},
  "score":   {"ok": true}, "export": {"ok": true}
}
```

**`price.loaded` 的判定规则（QA 别写错）**：`loaded:false` 有**两种合法情况**——① 本次是幂等空跑（`targetDates` 为空，pipeline 提前结束）；② T03 尚未落地（step_ts/step_rolling 还是空桩）。
所以能判定「有人在偷偷自己读价格宽表」的条件必须是**三者同时成立**：`ok == true` **且** `targetDates` 非空 **且** T03 已落地，此时 `price.loaded` 仍为 `false` 才是缺陷。T03 落地前 `loaded:false` 一律不算问题。

## 8. freshness 判定表（唯一实现，两页共用）

```
dataThrough     = SELECT MAX(date) FROM factor_panel                     # 0.0s
expectedThrough = SELECT MAX(date) FROM stock_daily WHERE date <= today   # 4.95s
lagTradingDays  = SELECT COUNT(DISTINCT date) FROM stock_daily
                  WHERE date > dataThrough AND date <= expectedThrough
lastCalcOk      = factor_run.read().ok

判序（先命中先返回）：
1. lastCalcOk === false                       → failed   reason = error[:120]
2. lagTradingDays === 0 且 dataThrough 非空    → fresh    reason = null *或* 中断提示   ← 必须是第 2 条
3. running 有效 且 lagTradingDays > 0          → pending  reason = "今日重算进行中"
4. lagTradingDays >= 2                        → stale    reason = "已过期 N 个交易日"（若 running 已过期，附加中断提示）
5. 今日工作日且 now >= factor_time 且 lag > 0   → stale    reason = "今日未完成重算"（若 running 已过期，附加中断提示）
6. 其他（未到点 / 非交易日）                     → pending  reason = "今日尚未到重算时点"
```
（`running 有效` 的定义见下方有效期守卫；`*` 见「`fresh` 的 reason 也可以非空」。）

**为什么 `lag` 必须排在 `running` 前面（踩过的坑）**：`step_export` 在第 8 步写 `factor_api.json`，此时整轮还没 `finish()`、`running` 还在。若 `running` 排在前面，导出那一刻就会把 `pending`「今日待更新」写死进文件，而导出之后不会再有人导一次 → **这个错误状态挂一整天**：16:08 已经算完，页面却说没跑成。任何正常跑完的日子都会中，与 `partial` 无关。

**原理**：「**数据到不到位**」看 `lag`，「**有没有进程在跑**」看 `running`，这是两个正交维度。顺序写反就会得到「已更新却显示待更新」这类自相矛盾的状态。

**`running` 的有效期守卫：A + B 两件都要做，职责不同**

`running` 是持久化的，若某次运行被强杀（未走 `finish()`），它会永远停在 `true`，规则 3 就会让页面永久停在「今日重算进行中」。这不是一个方案的两种写法，而是两个不同层面的修复：

| 方案 | 位置 | 保住什么 | 单独做的后果 |
|---|---|---|---|
| **A 读时判过期** | `freshness.compute()` | **页面**不被脏 `running` 卡死 | 状态文件里的脏值一直留着，每次读都判一次过期（无害但一直脏） |
| **B `begin()` 时清残留** | `factor_run.begin()` | **状态文件**本身保持干净，并记 warning | 今天剩下的时间页面仍卡「重算中」= 等于没修 |

`running` 仅在 `startedAt` 距现在 **≤ 90 分钟**（= 子进程 `timeout 3600s` + 余量）内才视为**有效**。

**⚠ 过期后不能直接返回 `fresh`（这是比原 bug 更危险的写法）**

`running` 过期只说明「那个进程可能已经死了」，**并不说明数据是新的**。所以逻辑必须是：忽略过期 `running` → **继续按 `lag` 判定**：

```
running 存在但已过期 → 忽略它 → 继续往下判
  lag == 0 → fresh   （数据确实到位，进程可能只是没走 finish）
  lag > 0  → stale   reason = "上次运行疑似中断，数据停在 <dataThrough>"
两种情况都要在 reason 里注明：「上次运行未正常结束（startedAt=<X>，已超过 90 分钟）」
```

若「过期即 fresh」，会出现「进程死了、数据也没更新、页面却显示最新」——这比原来的 bug 危险得多，因为它让人以为可以放心用。

**`fresh` 的 reason 也可以非空**

不要为了维持「`fresh` → `reason=null`」的对称性把信息丢掉。`fresh` + `reason="上次运行未正常结束（startedAt=…，已超过 90 分钟），但数据已到位"` 是完全合法的组合：它同时表达「数据可用」和「本次收尾异常」两件事，后者对排障有用。前端渲染时 **`reason` 非空就显示**，不按 `state` 过滤。

**`status` 与 `reason` 可以同时非空（`fresh` + `NO_CALC_REASON`）**

新流程尚未运行过、但面板数据已经到位时，正确的组合是 `status=fresh` **且** `reason="尚未运行过本次重算（NO_CALC_REASON）"`——「数据是最新的」和「这一版结论还没跑过」同时成立。所以：

- `reason` 的可空性**不随 `state` 变**，任何状态下都允许非空
- 前端规则固定为「**`reason` 非空即显示，不按 `status` 过滤**」；这条规则存在的目的就是为这类组合留位置
- 推论：不要用 `reason === null` 反推「一切正常」，也不要因为 `fresh` 就把 `reason` 清空

（字段命名提醒：实现与前端现在混用 `state` / `status` / `statusLabel`。语义以本表为准，命名须在 T05 统一为 `state`，其余为展示层别名，避免同一份数据出现两种状态名。）

**`freshness` 对象的字段边界（导出文件里只放结果，不放运行状态）**

同一个字段在两类文件里合法性不同，`running` 就是典型：

| | `factor_run.json` | `factor_api.json` / `factor_score.json` |
|---|---|---|
| 文件性质 | **状态文件**（可含瞬态） | **导出文件**（只放结果） |
| `running` | ✅ 合法，它就是要表达「当前在跑」 | ❌ 禁止，导出那刻恒为 `true`，永远不会再更新 |
| `nextRunAt` | ✅ | ✅ 计划值，确定值，可固化 |

```
允许出现在导出文件 freshness 的字段：
  state, dataThrough, expectedThrough, lagTradingDays, reason,
  lastCalcAt, lastCalcOk, lastCalcError, nextRunAt,
  cacheVerify{ok, checked, maxRelErr, axisMode, reconcile{...}}

禁止出现：
  running / busy / phase / 任何"当前正在做什么"的字段
```

理由：导出发生在进程内部，**导出那一刻 `running` 恒为 `true`**，写进文件就成了一句永远不会更新的假话——文件停在磁盘上，`running:true` 却永久不变。
页面若要显示「正在重算」，读 **`/api/scheduler/status` 的 `busy.factor`**（实时字段，已存在），不要读导出文件。

注意与 `nextRunAt` 的区别：`nextRunAt` 是**下次计划时间**，是确定值、不随"时间流逝"变化，可以固化；`running` 是瞬态，不可以。两者不要一起禁掉。

`nextRunAt` 由 `sched_time._next_run()` 产出，与 `/api/scheduler/status.next_factor` **同一个函数**，杜绝两处时间对不上。

## 10. 共享知识（跨文件必须统一，16 条）

1. **时间源唯一**：业务时间只来自 `data/factor_run.json`
2. **时间格式**：`factor_run.json` 用 ISO `YYYY-MM-DDTHH:MM:SS`（本地时间无时区）；`nextRunAt` 用 `YYYY-MM-DD HH:MM`；日期键 `YYYY-MM-DD`；页面只切片展示
3. **状态枚举（小写，只此 4 个）**：`fresh | pending | stale | failed`。`failed` 优先
4. **因子判定档位唯一来源 `export_factor_api.verdict_of`**：`值得复核 / 方向需翻转 / 仅统计显著 / 未达门槛 / 数据不足`；滚动选中集合 = `{值得复核, 方向需翻转}`
5. **口径常量**：`HORIZON=5`、`ENTRY="s1_open"`、`MIN_STOCKS=100`、`NW_LAG=4`、`ROLL_STEP=20`、`ROLL_SELECT_WINDOW=120`、`WARMUP_BARS=300`。全部走配置并写进 JSON
6. **退出码**：`0` 成功/幂等空跑（**含「滚动无有效期但打分导出照常」的 `partial` 情况**）；`2` 校验失败；`3` 运行锁占用；`4` **仅「连打分都做不出来」时**的硬失败（滚动无有效期本身不触发）；`5` 打分/导出异常；`124` 超时
7. **原子性铁律**：`factor_run.json` / `panel_cache/meta.json` / `factor_ts/meta.json` / `factor_score.json` / `factor_api.json` / `factor_rolling.json` 一律 `.tmp → os.replace`；`panel_cache/*.npy` 只在 `commit_stage()` 内替换；`factor_ts/*.npz` 只在 §5.6 第 6 条的重算校验通过后替换
8. **失败不可静默**：失败必须同时（a）`factor_run.error` 有值（≤120 字）、（b）非零退出码、（c）不覆盖任何产物
9. **无前视铁律**：时点 T 的判据只能用 `date <= T - horizon`；`ic_cutoff()` 是唯一入口，禁止别处写 `ic.loc[:T]`
10. **轴铁律**：`meta.dates/symbols` 只允许尾部追加，永不重排；`load()` 必须做形状校验
11. **中文标签**：分类中文名只从 `factors.registry.CATEGORY_LABELS` 取，前端不硬编码
12. **`ts.ic` = 未乘 direction 的原始 IC**：方向一致性只体现在 `ts.groups`（`group_returns` 内部已按 direction 归正）。`recent_validity` 用的是方向修正后的 IC，两者符号相反属正常，**页面不得把它们并列比较**。`verdict_of` 只看 `abs(t_nw)` + `monotonicity`，语义自洽。
13. **`ts.last <= panelMax - horizon` 是约束 A 的数据层探针**：滞后 `>= horizon` 都正常（`min_stocks=100` 会让个别日子无 IC），只有 `< horizon` 必为错误实现。它与 `ic_cutoff()` 的切片层断言构成两道防线，禁止删掉任何一个。
14. **`reconcile.state` 由 `factors[].state` 派生，禁止独立判定**：`suspect`（任一因子 suspect）> `warn`（跨口径 `maxAbsDiff>1e-3` 或 `extraPct>5%`）> `ok`。两类偏差字段分开（`dataWarn` = 数值差、`caliberWarn` = 口径差异），文案不得合并。`warn` 照常用、`suspect` 才跳过——两者混同会让用户不知道该信到什么程度。**`maxAbsDiff` 是跨口径比对，阈值必须与同口径的 `PROTECT_RTOL=1e-5` 分开**（用 1e-5 会让 warn 永远常驻）。
15. **依赖缓存的步骤必须显式断言缓存命中，不得依赖静默回落**：`panel_cache.load()` 未命中返回 `None` 后，`load_panel_wide` 会**静默回落逐因子 SQL**（秒级 → 分钟级，且不报错）。因此 `factor_ts.ensure()` / T03 任何读面板的步骤，入口一律先 `coverage()` 断言 24 因子齐备、不齐 `exit 2`。**「只是变慢」是最难查的一类故障，必须让它变成「直接失败」。**
16. **导出型 JSON 只放「这次运行产出的结果」，不放「当前的运行状态」**：`running` / `busy` / `phase` 属于后者，**任何时刻快照都必然失真**——写文件时进程一定在跑，所以 `running` 写进导出文件永远是 `true`，而文件不会自己更新，成了一句话不会变的假话。页面要显示「正在重算」就读 `/api/scheduler/status` 的 `busy.factor`。
    **判定的第一步不是看字段本身，而是先看它落在哪类文件里**：
    - **状态文件**（`factor_run.json`、`scheduler_state.json`）：可含瞬态（`running`、`busy`、`phase`），因为它被实时读、且会被下一次运行覆盖
    - **导出文件**（`factor_api.json`、`factor_score.json`、`factor_rolling.json`）：只放结果，禁止任何瞬态
    同一个字段在两类文件里合法性不同，`running` 就是典型（§8 有对照表）。
    对导出文件再问一句：**这个字段的值，会不会因为你「没做任何事、只是过了一段时间」而变化？会 → 不该固化。**
    **但这一问还不够。** 本轮 `freshness.py` 曾出现 `lastCalcAt = null` 却给 `status=fresh / statusLabel="数据已更新"`——它**不随时间变化**（永远是 `fresh`），所以第一问拦不住它，而它实际是在**声称一次从未发生的更新**。
    因此加第二问：**这个值能否被当前状态证实？**「已更新」必须有 `lastCalcAt` 非空才可证实；没有 `lastCalcAt` 就只能说「尚未运行过」（§8 的 `fresh + NO_CALC_REASON`）。
    **两问都过才算合格**：① 不随时间流逝而变；② 有当前状态作为证据。
    注意例外：`nextRunAt` 是**下次计划时间**，是确定值、不随时间流逝而变，**可以**固化——不要把「瞬态」和「计划值」一起禁掉。

## 11. 运维流程

**上线前一次性（手动，不进定时任务）**
1. `python panel_cache.py --coverage` → 确认缺哪几个因子（截至 T02 上线时缺 17 个）
2. `python panel_cache.py --build-all` 补齐（约 60–90 分钟），完成后再次 `--coverage` 确认 **24/24**
3. `python panel_cache.py --verify --verify-mode full` 过轴逐项比对与数值校验
4. 初始化 `data/factor_ts/`（约 100 秒，按 `min_stocks=100` 全量重算 `ic`+`groups`）。**入口自带 `coverage()` 断言，缓存不齐会直接 `exit 2`**——这是有意的：静默回落会把它变成分钟级且不报错（§10 第 15 条）
5. `python run_factor_pipeline.py --trigger manual` 全链路验证：看 `factor_ts` 与 `factor_eval.json` 的对账 warning，以及 `verify` 段里 `price / ts / rolling / score / export` 五个探针是否都填上了

**日常（自动）**
- 15:40 增量补 K 线 → 15:50 策略扫描 → **16:10 因子重算**
- 因子任务启动先 `coverage()` 断言 24 因子齐备，不齐 `exit 2`

**手动触发**
- `POST /api/scheduler/run?job=factor`（返回 202 + busy 状态）
- 或直接跑 `run_factor_pipeline.py --trigger manual`

**缺口多日**
- 自动只补最近 30 个交易日，剩余下次继续；仍超限则提示改走全量重建

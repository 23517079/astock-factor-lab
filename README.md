# A 股因子研究与验证系统

一个自建的量化研究工作台：**从全市场日线数据出发，做因子挖掘、逐期滚动评估、扣费验证，最后给出可追溯的候选池**。配套一个本地 Web 终端，把每个数字的来源、可信度、以及它是否值得相信，都摆在页面上。

这个项目最特别的地方不是"能跑出收益曲线"，而是**它会主动拦住自己**：前视偏差算错会被断言拦下，成本翻倍后结论不成立会把绿灯关掉，因子方向用反会在报告里自曝并给出修法。

> 本仓库只包含**代码 + 结论快照**。原始数据库约 25 GB、面板缓存 683 MB，保存在本地，不纳入版本控制。

---

## 一、它解决什么问题

个人做量化最容易掉进的三个坑，这个项目逐个设了机器闸门：

| 坑 | 常见表现 | 本项目的闸门 |
|---|---|---|
| **前视偏差** | 用全样本挑因子、用未来数据定方向，回测漂亮实盘失效 | `ic_cutoff` 唯一判据 + 切片函数内部 `raise` 断言 |
| **成本幻觉** | 忽略印花税/过户费，年化虚高几个点 | 分时段费率表按**成交日**取档，扣费后重算全部指标 |
| **数据自欺** | 单源数据当双源验证，时点不可比却标"已核对" | 四态数据契约 + 字段级对账 + 统计校准的容差 |

## 二、三个可复核的技术看点

### 1. 前视偏差：用断言而不是靠自觉

滚动评估的核心是一个纯函数：

```python
def ic_cutoff(dates, t, horizon):
    return dates[t - horizon]      # 第 t 期只能用 t-horizon 及之前的数据
```

判断"某日该用哪一期信号"的唯一入口是 `ic_cutoff(t) <= d - horizon`，**不是** `asOf`。更关键的是 `factor_ts.slice_until()` 内部有 `raise` 断言——只要切片越过 cutoff 就直接报错，而不是安静地给出一个偏乐观的数字。

实测证据：24 个因子、70 期滚动、`step=20 / window=120 / horizon=5`，逐期核验 `icCutoff` 严格等于 `asOf − 5` 个交易日。

修正前后对比同样留档：修正前 12 个因子里有 6 个（全为动量类，先验方向为 +1）**方向用反**，Top10 与修正版重合 0/10。

### 2. 扣费验证：让结论自己失效

费率不是拍一个统一数字，而是三段分时表，按**卖出日**选档，还原历史制度变化：

- 印花税 2023-08-28 减半
- 过户费 2022-04-29 降档

当前一轮综合成本约 **31.2 bp**（最新产物，12,941 笔 / 1,296 个买入日）：

| 情景 | 净年化 (Top10) | NW t 值 | 十分组净价差 | 判定 |
|---|---|---|---|---|
| 计入真实费率 | **+10.79%** | 0.73 | +16.45% | weak |
| 费率 ×2 | **−6.34%** | −0.47 | +16.39% | **fail** |

门禁结论：`passed: false / level: fail`，理由「扣费后：weak」「费用翻倍：fail」。**页面上的绿灯不会亮。**

这里有一个反直觉但很重要的发现：**因子层 IC 极其显著（IC 均值 0.052，ICIR 6.14，NW t = 8.22），但组合层净收益的 NW t 只有 0.73。** 因子有效不等于组合能赚钱——横截面择时能力被换手成本和分组离散度稀释掉了。如果不做扣费和敏感性分析，只看 IC 会得出完全错误的结论。

另一条必须写死的纪律：**不能用 IC 证明扣费后有效**。统一费率是横截面单调变换，`(1+fwd)×k[d]−1` 不改变同日排名，Spearman IC 天然不含成本信息。扣费证据只能看净年化、NW t 和翻倍敏感性。

### 3. 数据可信度：单源不伪装，冲突不静默

每个接口返回都套一层契约，状态分四态：`ok / degraded / incomplete / failed`，并附带 `issues[]` 与 `verification`。

容差不用经验值，而是**统计校准**：按价格量级抽样历史数据 + 三源实时横截面，取 P99 写入 `tolerance.json`，并区分两个时段：

- `closed`（收盘）：0.02 元 / 0.0002 / priceMax 0.10 / 0.05pp
- `intraday`（盘中）：0.10 元 / 0.001 / priceMax 0.50 / 0.30pp

早期用 0.5% 当容差，导致茅台（1700 元）的容差高达 7.18 元，真实冲突被漏报——这就是为什么必须校准而不是拍脑袋。

对账结果分 `match / mismatch / unverifiable`。其中 `comparability=time-skew` 表示**有第二源但两源时点不可比**，既不算冲突也不算已验证，两个数值都保留。盘前会额外标注 `marketState=pre-market`，避免状态是 `ok` 却说结论不可用。

## 四、工程约束是怎么落到代码里的

- **数据只增不改**：面板增量追加，跳过最后 `horizon` 天（未来收益还没发生）
- **业务时间唯一源**：`data/factor_run.json` 是唯一时间基准，避免多处时钟漂移
- **单源不装扮成双源**：本地 K 线只做同源新鲜度校验，绝不标"独立第二源已验证"
- **失败不降级成静默**：小样本排不出评估期时，明确降级为 `legacy` 模式并写 `partial + warning`，同时注明"含轻度前视"，而不是装作正常
- **测试不依赖生产偶然状态**：曾有三条用例靠"生产 JSON 恰好缺字段"达成，产物一更新就变假红——已改为构造输入

## 七、本地运行

需要 Python 3.10+ 与 Node 20+，以及一份本地行情库（不在仓库内）。

```bash
# 1. 计算服务
cd sequoia-service
pip install -r requirements.txt
python server.py                      # :8791

# 2. 前端
cd ../astock-analyst
cp data/config.example.json data/config.json   # 填入你的 LLM 密钥
node server.js                        # :8790
```

Windows 下可直接双击根目录 `启动.bat`。

## 八、关于本仓库的诚实说明

- **云端不跑计算**：GitHub Actions 只做测试与静态页面渲染。全量流水线依赖 25 GB 本地数据库与境内行情接口，境外 runner 抓 A 股数据不可靠，所以重计算留在本地。
- **不含原始数据**：`data/*.json` 是结论快照，用于展示与复核，不能直接复现完整回测。
- **已知未修的问题**：个股分析接口的名义主源（东财 `stock/get`）实际只返回部分字段，长期退化为新浪单源；修正会影响 PE、量比等字段，需单独排期。这条写在代码注释和这里，而不是藏起来。
- **`sequoia_x/` 的 DataEngine 与策略骨架**源自开源项目 Sequoia-X，本项目做了改造与适配；因子流水线、评估、扣费验证、数据契约层为自建。
